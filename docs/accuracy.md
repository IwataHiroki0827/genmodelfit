# 見積もりの精度 / Accuracy

2026-10-20 時点。係数は `src/genmodelfit/data/calibration.json`、作り直しは `python -m genmodelfit.calibrate`
(`--dry-run` で書き出さずに表だけ出す)。下の表はそのコマンドの出力をそのまま貼ったもの。

## 結論

- 実測 9 件(すべて RTX 5080 16GB)のうち、GPU の上限に張り付いていない 6 件で、
  **leave-one-out(1 件ずつ外して残りで合わせ、外した 1 件を当てる)の平均絶対誤差 4.9%、最大 17.0%**。
  張り付いた 3 件は 3 件とも「予測 ≥ 実測」で矛盾しない。**目標 ±20% は、この 9 件の範囲では達成**
- ただし点が少なく、達成と言える範囲は狭い(下の「分かっている限界」)。特に **動画と音声は実測が 1 件ずつなので、
  その 1 件を外すと係数は事前値に戻り、LOO の誤差は事前値の当たり外れを測っているだけ**
- 比べる基準として「ファイルの大きさの合計だけ」で当てると平均 15.2%(最大 26.1%)。作業用メモリと固定分を足すことで
  4.9% まで縮んだが、縮んだ分の大半は固定分(約 0.8 GB)で説明できる
- 合わせたのは「全部載せ」の VRAM(`vram_gb`)だけ。**「順に載せ替え」(`vram_sequential_gb`)と
  「逃がす」(`vram_offload_gb`)は実測が無く、検証していない**(8GB の GPU での実測が要る。#5 の bench)

## 式

ComfyUI は「文章の読み取り(テキストエンコーダ)→ 生成(本体)→ 仕上げ(VAE)」を順に動かす。そこで重みを段ごとに分け、
3 つの量を出す(`estimate.py`)。

| 量 | 式 | 意味 |
|---|---|---|
| `vram_gb`(全部載せ) | 固定分 + 全部品の重み + 作業用メモリ | 動的 VRAM が空きの多い GPU で使う量。実測で合わせたのはこれだけ |
| `vram_sequential_gb`(順に載せ替え) | 固定分 + max(エンコーダ, 本体 + 作業用, VAE + 作業用, その他) | 段の間で部品を降ろす。少し遅いが普通に使える |
| `vram_offload_gb`(逃がす) | 固定分 + max(各段の重み × 0.4 + その段の作業用) | 重みの一部をメインメモリに置いたまま動く(lowvram / 動的 VRAM)。遅い |
| `ram_gb` | 3.0 GB + 全部品の重み | 逃がした重みを置く場所。足りなければ動かない |

- **重みの分け方**: `ModelFile.role` → `directory` → ファイル名(`vae` / `text_encoder` / `t5` / `clip` / `qwen` など)の順で決める。
  1 ファイルに全部入りの `checkpoints` は、safetensors の見出しのテンソルの大きさで数えた内訳で分ける
  (SDXL / ACE-Step 1.5 / Hunyuan3D 2.0 / 2.1。2026-10-20 に読んだ)。内訳の分からない全部入りと、ファイル情報が無く
  テンプレートの大きさしか無いものは、本体 75%・エンコーダ 20%・VAE 5% で分ける(この割合は検証していない)
- **作業用メモリ**: 画像 = 係数 × メガ画素 × 枚数、動画 = 係数 × メガ画素 × (コマ数 / 49)^0.5、音声 = 係数 × 分、3D = 一定。
  動画の指数 0.5 は合わせていない(実測が 1 件しかない)。線形より緩くしたのは、ComfyUI の注意機構が省メモリの実装
  (SDPA など)で、トークン数に対して作業用メモリが 2 乗では増えず、Wan の VAE はコマを少しずつ区切って復号するため
  (コマ数がそのまま効かない)。指数の値そのものは根拠のある数字ではない
- **精度の指定**(`Settings.precision`、CLI の `--precision`): 本体の重みだけを換算する(例: bf16 → fp8 で半分)。
  元の精度は `ModelEntry.precision`、無ければ本体のファイル名(`bf16` / `fp8` / `int8` など)から読む。分からなければ換算しない
- **段階**: perfect = 全部載せが VRAM の 90% 以内 / good = 全部載せが VRAM 以内、または順に載せ替えれば載る /
  marginal = 逃がせば載る(または GPU 無しで CPU)/ too_tight = 逃がしても載らない、またはメインメモリ不足

## 実測の使い方

RTX 5080 の実測は ComfyUI の動的 VRAM で測ったもので、**空きがあれば多めに使う**。16GB で 13.2GB(Z-Image int8)は
必要量の下限ではない。そこで:

1. 実測は「全部載せ」(`vram_gb`)の値として使う。そのモデルの作業用メモリを「実測 − 式の値」だけずらし、
   同じずらしを順に載せ替え・逃がすの値にも足す。小さい GPU では全部載せが入らなくても、**順に載せ替え・逃がすへ落ちる**
   (例: 8GB で Z-Image int8 は全部載せ 13.2 GB だが、順に載せ替えて 7.2 GB で good。6GB では marginal)。
   実測の値が GPU より大きいことだけで too_tight にはならない
2. 実測が GPU の容量の 90% 以上(または offload が lowvram など)なら「上限に張り付いた」とみなし、
   **下限としてだけ使う**(全部載せ = max(式, 実測))。該当は Z-Image bf16(15.0 / 16)と Wan2.2 5B の 2 件(15.8 / 15.0)
3. 設定(解像度・コマ数・長さ・精度)が実測と同じときだけ `basis: "measured"`。違う設定は実測でずらした推定で
   `basis: "estimated"`(理由に「…の実測で補正した推定」と出す)。精度を変えたら実測は使わない
4. 設定を指定しないときは、実測のあるモデルは実測の設定(AI生成キットの「はやい」画質)で判定する。
   実測の無いモデルは種類ごとの既定(画像 1024px、動画 832x480・81 コマ、音楽 30 秒など)

## 合わせ方

- 合わせる係数は 5 つ: 固定分 `overhead_gb`、作業用メモリの `act_image_gb_per_mp` / `act_video_gb_per_mp` /
  `act_audio_gb_per_min` / `act_3d_gb`。重みの係数(1.0)・逃がす割合(0.4)・動画の指数(0.5)・メインメモリの固定分(3.0 GB)は固定
- 予測はどの係数にも 1 次なので、**相対誤差の 2 乗和**(張り付いた実測は予測が下回ったときだけ数える片側の 2 乗)に、
  事前値(#1 の仮の値。実測を見る前に決めたもの)からの相対的なずれへの弱い罰(重み 1e-4)を足し、
  物理的にありえる範囲の中で座標降下により最小にする。目的関数は凸なので結果は初期値によらない
- 9 件で 5 係数なので、罰が無いと当てはまりすぎる。罰を弱くしているのは、実測があるところでは実測を優先するため
- 精度は leave-one-out で測る(全件で合わせた予測は当てはまりの良さで、精度の指標にしない)
- **人が決めた目安**(AI生成キットのカタログの最低 / 推奨 VRAM)は、係数を合わせるのには使っていない。
  ただし逃がす割合 0.4 は実測で決められないので、目安と矛盾しない範囲(SDXL が 4GB で動く・bf16 の Z-Image が
  4GB では動かない、の 2 つから、今の係数で 0.24〜0.57)の中ほどを選んだ。目安との突き合わせは `tests/test_estimate.py` が行う

合わせた結果(2026-10-20、n = 9、うち張り付き 3):

| 係数 | 値 | 事前値 | 範囲 |
|---|---:|---:|---|
| overhead_gb | 0.8037 | 0.6 | 0.3〜1.5 |
| act_image_gb_per_mp | 0.381 | 0.5 | 0〜4 |
| act_video_gb_per_mp | 9.8461 | 2.4 | 0〜30 |
| act_audio_gb_per_min | 0.0(下限) | 1.0 | 0〜5 |
| act_3d_gb | 0.6131 | 2.0 | 0〜4 |

| モデル | 設定 | 実測 GB | 全件で合わせた予測 GB | LOO 予測 GB | LOO 誤差 | 重みだけの誤差 |
|---|---|---:|---:|---:|---:|---:|
| image_z_image_turbo_int8 | 768x768 | 13.2 | 13.20 | 13.20 | -0.0% | -7.8% |
| image_z_image_turbo | 768x768 | 15.0 | 21.72 | 21.72 | 張り付き(≥ 実測で当たり) | +37.9% |
| image_sdxl_simple | 832x832 | 8.0 | 8.01 | 8.02 | +0.3% | -13.3% |
| text_to_video_wan | 512x512・49 コマ | 13.3 | 13.21 | 11.04 | -17.0% | -26.1% |
| video_wan2_2_5B_ti2v | 640x640・73 コマ | 15.8 | 23.87 | 23.87 | 張り付き(≥ 実測で当たり) | +14.8% |
| video_wan2_2_5B_ti2v | 640x640・73 コマ・文章から | 15.0 | 23.87 | 23.87 | 張り付き(≥ 実測で当たり) | +21.0% |
| audio_ace_step_1_5_checkpoint | 20 秒 | 10.8 | 10.84 | 11.40 | +5.5% | -7.1% |
| 3d_hunyuan3d_image_to_model | - | 6.7 | 6.79 | 6.96 | +4.0% | -19.8% |

張り付いていない 6 件: 平均絶対誤差 **4.9%**、最大 **17.0%**(重みだけなら平均 15.2%)。張り付いた 3 件のうち 3 件で予測 ≥ 実測。
目標 ±20%: 達成。

読み方:

- 画像の 2 件は互いに当て合えている(Z-Image int8 と SDXL の作業用メモリの比がほぼ同じだった)。LOO が本当に
  「知らないモデルを当てる力」を測れているのは、画像の 2 件と 3D の 2 件だけ
- Wan2.1 の -17.0% と ACE-Step の +5.5% は、1 件しか無い種類の 1 件を外した結果なので、事前値(#1 の仮の値)で当てた誤差
- 音声の係数は下限の 0 になった。ACE-Step の実測と式の差(0.77 GB)が固定分(0.80 GB)で説明できてしまい、
  長さの影響が見えていない。**音声の「何秒まで」(`limits.max_seconds`)は、今は長さで VRAM が増えない前提の値**で、
  調べた上限(600 秒)まで good と出る
- 動画の係数(9.8 GB/メガ画素)は Wan2.1 の 1 件だけで決まっている。この 1 件の差(式より 3.5 GB 多い)には、
  動的 VRAM が空きに置いた分も入っている可能性が高い

## 分かっている限界

- **GPU が 1 種類だけ**: 9 件とも RTX 5080 16GB・動的 VRAM。小さい GPU での「順に載せ替え」「逃がす」の値は検証していない。
  Issue #4 にある RTX 3070 8GB の実測(#5 の bench)が入ったら、その 2 つを合わせる
- **動的 VRAM**: 空きがあれば多めに使うので、実測は「必要量」ではなく「その GPU で使った量」。全部載せの値も、
  空きの少ない GPU では実際より大きく出ている可能性がある
- **張り付いた実測**: Z-Image bf16 と Wan2.2 5B の全部載せの値は式だけで決まっていて、実測では上から押さえられていない
- **Wan の縦横比**: 動画の実測は長辺(512px / 640px)しか記録が無く、正方形と仮定した。実際が 16:9 なら画素数は
  約 56% で、動画の係数は 1.8 倍ほど小さく見積もり直すことになる
- **日付が不明**: 実測の日付・ComfyUI の版の記録が無い(measurements.json の date が空)
- **単位**: 実測が GB か GiB かの記録が無い。ファイルの大きさは 10 進の GB で数えている(GiB なら実測は 7% 大きい)
- **分かっている外れ**(人が決めた目安との突き合わせ、`tests/test_estimate.py` が strict な xfail で記録):
  - Wan2.2 5B は 8GB で too_tight、12GB で marginal と出る(目安は最低 8GB・推奨 12GB)。
    動画の作業用メモリを Wan2.1 の 1 件から伸ばしている(Wan2.2 は VAE の圧縮が強く、画素あたりのトークンが少ないのに
    同じ係数を使っている)ため厳しめに出る。8GB の実測で合わせ直すまで直さない(係数を目安に合わせて動かすと、
    この表の数字の意味がなくなる)
  - ほかの 7 モデルは、目安の最低 VRAM で too_tight にならず、推奨 VRAM で good 以上になる
- **メインメモリ**: 3.0 GB + 全部品の重みとして、足りなければ too_tight にしている。ComfyUI は safetensors を
  メモリに割り当てて読むので、全部載せで動くときは実際にはもっと少なくて済むことがある(安全側)。実測は無い
- **全部入りの内訳を知らないモデル**(#2 で増える HF のものなど)は一般的な割合で分けており、順に載せ替え・逃がすの値の誤差は大きい
