# 見積もりの精度

[English](accuracy.md) · **日本語**

genmodelfit の VRAM・メモリの見積もりが、どんな式でどの実測に合わせてあり、どこまで当たるかをまとめたページです。
見積もりを読む人、数字を直す人、実測を提出する人向けです。

2026-10-28・0.12.0 の時点(ほかの利用者の実測の扱いは 2026-10-22。作業用メモリの式は 2026-10-27 に段ごとの式に変えた: #100)。
係数は `src/genmodelfit/data/calibration.json` にあり、作り直しは `python -m genmodelfit.calibrate` です
(`--dry-run` で書き出さずに表だけ出します)。下の表はそのコマンドの出力をそのまま貼ったものです。
**単位はすべて GiB(2^30 バイト)**。表や CLI の「GB」も GiB を指します。

## 結論

- **#100(2026-10-27)から、作業用メモリは ComfyUI の作者の見込み(コードの式)を段ごとに使う**(下の「式」)。
  係数を実測に合わせるのは、当てられないモデルのうち 3D の 1 つ(`act_3d_gb`)だけになった。
- メンテナの RTX 5080 の張り付いていない 4 件(余裕のある GPU での山)との差は、Z-Image int8 +5.1%・SDXL +12.5%・
  Wan 2.1 1.3B −14.7%・ACE-Step 1.5 +9.2%(下の「結果」)。式に実測を合わせていないので、これは当てはめでなく照合。
  - 4 件・1 種類の GPU・動的 VRAM の山なので、「目標を達成した」とは言えない。
  - Wan 2.1 1.3B は、実測が式(VAE はタイルの値)より 1.96 GB 大きい。余裕のある GPU で、動的 VRAM が部品を
    載せたままにし、VAE もタイルに分けずに仕上げた山(タイルなしの VAE なら 14.04 GB で +5.6%)。
    この正のずらしは全部載せにだけ足す(下の「実測の使い方」1)。
- 3D の 2 件は leave-one-out(1 件ずつ外して残りで合わせ、外した 1 件を当てる)で +6.4%・−4.6%。
- **張り付いた実測 3 件(Z-Image bf16、Wan2.2 5B × 2)は情報を持たない**。
  - 重みだけで実測を超えるので、「予測 ≥ 実測」は式の作りから必ず成り立つ(外れようがない)。
- 比べる基準として「ファイルの大きさの合計だけ」で当てると、張り付いていない 6 件で平均 22.8% 外れる。
- **「順に載せ替え」(`vram_sequential_gb`)と「逃がす」(`vram_offload_gb`)、メインメモリ(`ram_gb`)は実測が無く、検証していない**。
  段ごとの山を測る bench(宿題)が要る。
- RTX 3070 の掃引(2026-10-27)は、GPU が上限に張り付き、ほかの作業が使っていた回があるので、精度の根拠にしない
  (下の「照合」。測り直す)。

## 式

ComfyUI は「文章の読み取り(テキストエンコーダ)→ 生成(本体)→ 仕上げ(VAE)」を順に動かします。
そこで重みを段ごとに分け、段ごとの作業用メモリ(#100、2026-10-27。下の「段ごとの作業用メモリ(#100)」)と合わせて、
3 つの量を出します(`estimate.py`・`working.py`)。

| 量 | 式 | 意味 |
|---|---|---|
| `vram_gb`(全部載せ) | 固定分 + 全部品の重み + max(S, V_eff, T) | 全部の重みが載ったまま、一番重い段の作業用メモリ |
| `vram_resident_gb`(載せたまま) | 固定分 + 全部品の重み + max(S, V, T)(V はタイルにしない値) | 全部載せの動かし方を選べるかだけに使う(98% を超えたら全部載せは選ばない。下の「タイル」。#102) |
| `vram_sequential_gb`(順に載せ替え) | 固定分 + max(文章の段の重み + T, 生成の段の重み + S, 仕上げの段の重み + V_eff, その他) | 段の間で部品を降ろす。少し遅いが普通に使える |
| `vram_offload_gb`(逃がす) | 固定分 + max(各段の重み × 0.4 + その段の作業用メモリ) | 重みの一部をメインメモリに置いたまま動く(lowvram / 動的 VRAM)。遅い |
| `ram_gb`(GPU に載せて動くとき) | 3.0 + いちばん大きい段の重み | 全部載せ・順に載せ替えのとき(下の「メインメモリ」) |
| `ram_gb`(逃がす・CPU のとき) | 3.0 + 全部品の重み | 逃がした重みがメインメモリに居続ける |

- S・V_eff・T は生成・仕上げ・文章の段の作業用メモリ(下の「段ごとの作業用メモリ(#100)」)。
- 段ごとに当てられないモデル(下の「当てられないモデル」)は、モデル全体を今までの式で出す
  (作業用メモリは種類ごとの係数の式で、生成の段と仕上げの段に同じ量。文章の段は 0)。段ごとに混ぜない。
- 固定分は 0.10 で合わせた 1.472 GiB のまま(合わせ直さない。下の「合わせ方」)。
  ComfyUI 自身の予約(`minimum_inference_memory` = 0.8 GiB + `EXTRA_RESERVED_VRAM`: Windows 0.6 GiB(15 GB を超える GPU は 0.7)・
  ほかは 0.4。model_management.py:877-891@426f5ee)の 1.2〜1.5 GiB とほぼ同じ。
  ただし動的 VRAM(下)ではこの予約の意味が変わる(重みは要るときに読み込み・追い出すので、空きを守る量ではなくなる)。
- #95 の下限(重み + 固定分)は S = V = T = 0 の値で、定義は変えていない。

**重みの分け方(役割)**: 次の順で決め、どれにも当たらなければ本体にします。

1. ComfyUI の置き場所(`directory`)
2. 明示した `role`
3. HF のフォルダ名
   - `unet` / `transformer` → 本体
   - `text_encoder*` / `tokenizer*` → エンコーダ
   - `vae*` → VAE
   - `image_encoder` → 画像エンコーダ
   - `controlnet` → 本体と同じ段
4. 知っているファイル名
   - テキストエンコーダ: `umt5` / `t5xxl` / `clip_l` / `clip_g` / `qwen_2.5_vl` / `qwen_3_4b` / `gemma` / `llama_3` など
   - VAE: `vae`

補足:

- `qwen` のような短い語では引かない(`qwen_image_fp8_e4m3fn.safetensors` は本体)。
- 本体と同時に GPU に載る部品(`controlnet`・`model_patches`・`loras` など)は生成の段に入れる。
- 音声エンコーダ(`audio_encoders`)は生成の前に動くので、読み取りの段に入れる。

**1 ファイルに全部入りの `checkpoints`**:

- safetensors の見出しのテンソルの大きさで数えた内訳で分ける(SDXL / ACE-Step 1.5 / Hunyuan3D 2.0 / 2.1。2026-10-20 に読んだ)。
- 次のものは、本体 75%・エンコーダ 20%・VAE 5% で分ける(この割合は検証していない)。
  - 内訳の分からない全部入り
  - ファイルごとの大きさが無く、テンプレートの大きさしか無いもの

### 段ごとの作業用メモリ(#100)

**根拠**: ComfyUI の作者が、各モデルの作業用メモリとして見込む量(ComfyUI のコードの式。一次資料)。
ComfyUI(GPL-3.0)のコードは import も写しもせず、数と式の形だけを `ファイル:行@426f5ee`(v0.43.0)の出典つきで
`src/genmodelfit/working.py` の表に持つ(表の 1 行が 1 つの鍵)。0.40.0(製品のエンジン)と違う所は書く。

- ComfyUI 0.40 以降の NVIDIA(と ROCm 7.14 以上の AMD)の既定は動的 VRAM(comfy-aimdo)で、ComfyUI の見込みは
  載せ方を決めない(重みは要るときに読み込み・追い出す。main.py・model_patcher.py・model_management.py)。
  だから「ComfyUI と同じ式なら動かし方を当てられる」とは言わない。言えるのは「ComfyUI の作者が見込む量」まで。
  動かし方を当てる意味があるのは、古い動き(`--disable-dynamic-vram`・torch 2.8 未満・ROCm 7.14 未満・Intel・Apple)だけ。
- **補正の倍率は掛けない**。画像の VAE の見込みは実測の約 1.8 倍の多め(RTX 3070 の掃引)だが、点が少ないので安全側として残す。

**S(生成の段)**: `S = 枚数 × 面積 × 2 バイト × 0.01 × 係数 MiB`(model_base.py:424-446@426f5ee の SDPA の経路の式)。

- 1 倍(1 回分)。ComfyUI は `memory_required × 1.5 < 空き` のときだけ cond と uncond をまとめて流し、
  足りなければ 1 つずつ流す(samplers.py:273-284)。動くのに要るのは 1 倍(`minimum_memory_required`、sampler_helpers.py:178)。
- 面積 = 潜在の要素数からチャンネルを除いたもの(画像は (H/s)·(W/s)、動画は 潜在のコマ × (H/s) × (W/s)、音声は潜在のコマ)。
- 潜在を詰めた形で渡す系統(LTX-2 / 2.3 の LTXAV・MiniMax H3。動画と音声の NestedTensor)は、面積にチャンネルと
  音声の潜在も入る(samplers.py:1281-1283、utils.py:1445-1453)。
- 編集の用途(`i2i`・`relight`)で、参照の潜在(`ref_latents`)を見込む系統(Flux・Flux2・Qwen Image・Z-Image・Lumina2 など。
  model_base.py の `memory_usage_factor_conds`)は、入力の画像 1 枚分の面積を足す。
- 係数は supported_models.py の `memory_usage_factor`(下の「系統の当て方」)。
- **会社によらず SDPA の式**。Apple(MPS)・CPU・対応外の AMD は分割式の注意機構(sub-quadratic)だが、
  分割式の見込み(× 0.15)は空きに合わせて分割する実装に対して「too aggressive」と ComfyUI 自身が書いており
  (model_base.py:444)、使わない。その GPU では理由に「作業用メモリが多くなることがある」と出すだけ(段階は変えない)。
  AMD で SDPA を使うのは gfx90a・942・950・1100・1101・1150・1151・1170・1171、ROCm 7 以上の gfx1200・1201
  (model_management.py:527-532、`estimate.AMD_SDPA_TARGETS`)。
- 生成の段を fp32 で計算する GPU(docs/hardware「精度」)は 2 倍。

**V(仕上げの段)**: VAE ごとの `memory_used_decode` / `memory_used_encode`(sd.py)。

- 1 枚分(ComfyUI は空き ÷ V で枚数を分ける。sd.py:1282-1283)。枚数は掛けない。
- 入力の画像・動画・音声を潜在にする用途(`i2i`・`i2v`・`v2v`・`inpaint` など)は、符号化も数える:
  V = max(復号, 符号化)。符号化する入力は、動画全体の用途(`v2v`・`control`・`inpaint` など)と Wan(画像から動画でも
  全部のコマを符号化する: nodes_wan.py:48・54)はコマ数ぶん、ほかは画像 1 枚。
- VAE の dtype: working_dtypes に fp16 が無い VAE(KL・Flux2(0.40)・LTX・Mage)は、bf16 の無い GPU で 4 バイト(2 倍)。
  float32 だけの VAE(LTX-2 の音声など)はどの GPU でも 4 バイト。
- AMD では KL の VAE(Flux2 の VAE も)を × 2.73(`VAE_KL_MEM_RATIO`、sd.py:503-506)。理由に出す。
- **Flux2 の VAE は × 4**(KL の式を 16 倍圧縮の潜在に当てたもの × 4)。0.40.0 は常に × 4(sd.py:693@0.40.0)、
  426f5ee は fused norm が使える GPU で × 1(sd.py:698)。製品のエンジンが 0.40 なので × 4 を使い、理由に出す。
- 系統ごとの VAE: 下の「系統の当て方」。LTX-2 / 2.3 は音声の VAE(float32、sd.py:991-992)の大きいほう、
  MiniMax H3 も音声の VAE(sd.py:1089-1096)の大きいほうを取る。

**T(文章の段)**: ComfyUI が作業用メモリを見込むテキストエンコーダ(sd.py:469-474 の `memory_estimation_function`)だけ。ほかは 0。

| 系統 | 式(bf16 の GPU。bf16 の無い GPU は 2 倍) | 出典 |
|---|---|---|
| ACE-Step 1.5 の LM | 5 × 秒 トークン × 0.4375 MiB(4B の LM は 0.5625)× 0.5 | text_encoders/ace15.py:243-246・323-326・384-391 |
| LTX-2 / 2.3 の Gemma | 最低 642 トークン × 6 MiB × 0.5 ≈ 1.88 GiB | text_encoders/lt.py:246-256 |
| YuE2 | 曲の段の長さ L = 秒 × 25 + 2 で、(2 × 28 × 8 × 128 × L + L² + L × 34816) × 2 バイト | text_encoders/yue2.py:129-137 |

- トークン数はテンプレートの既定が分からないので最低の値(YuE2 の楽譜の段(既定 8192 トークン)は入れていない。宿題)。
- Ming の画像のエンコーダ(text_encoders/ming_image.py:332)も見込みを持つが、Ming は VAE の式が無く当てられない(今までの式)。

### タイル

使う量(全部載せ・順に載せ替え・逃がす)に入れる V は **V_eff = min(V, V_tile)**。ComfyUI は VAE の復号の前に V を空けようとし
(sd.py:1278-1280@426f5ee)、入らなければほかのモデルを降ろし、それでも OOM が出ると VAE をタイルに分けて動かす
(sd.py:1269-1357・1422-1474)。V_tile は **VRAM によらない最小のタイル**の値にする(VRAM を増やして段階が下がらない)。

全部載せの動かし方を選べるかは、**タイルにしない V** で決める(#102、2026-10-28): 載せたままの量
`vram_resident_gb` = 固定分 + 全部品の重み + max(S, V, T) が 98% を超えるなら、ComfyUI は仕上げの前に本体を降ろすので、
全部載せは選ばず、順に載せ替え(Good まで)か逃がすにする。RTX 5080 16GB の 21 回で、ComfyUI が一部を降ろしたかが
20 回当たった(V_eff では 12 回。下の「照合」)。使う量を V にしないのは、実際に使う作業用メモリが V の 0.5〜1.0 倍で、
ピークの予測が悪くなるため(V は ComfyUI が載せ方を決める見込み)。実測のずらし d は負のときだけ足す(正のずらしの実測には
VAE の山がもう入っている)。実測で段階を決めた行には使わない。
SeedVR のように見込みが確かな VAE(`comfy_decode_estimate_is_reliable`)は、OOM を待たずに初めからタイルに分ける
(sd.py:1286-1291@426f5ee)が、ほかは上のとおり。

| 形 | 復号のタイル | 符号化のタイル |
|---|---|---|
| 画像(2D) | 潜在 64×64・32×128・128×32 の大きいほう(画像の潜在の大きさまで。sd.py:1182-1194)。8 倍圧縮で 512px 角、16 倍圧縮(Flux2・Qwen Image 2.1・Mage)で 1024px 角 | 画素 512×512・256×1024・1024×256 の大きいほう(sd.py:1214-1225) |
| 動画(3D) | 時間 2 コマ(1 コマなら 1)・空間 `256 / 圧縮` 角(潜在の大きさまで。sd.py:1335-1357) | 空間 256 画素角・時間はそのまま(sd.py:1462-1470) |
| 音声(1D) | 潜在 256 コマ(sd.py:1196)。ACE-Step 1 は同じ | 256 × 2048 サンプル(ACE-Step 1 は 1/16。sd.py:1227-1235) |
| 自分でタイルに分ける VAE(MiniMax H3) | 256 画素角(sd.py:1327-1331・1335) | 256 画素角 |

- ComfyUI の 3D の予算 `min(V, 総量 × 0.8)` は VRAM による値なので、段階には最小のタイルを使う。
- V が GPU に入らないとき(固定分 + 仕上げの段の重み + V > VRAM)は、理由に「VAE をタイルに分けて動かす(遅い)」と出す
  (V_eff の段階は変えない)。Windows の NVIDIA は共有メモリへのはみ出し(sysmem fallback)で OOM にならず、遅くなるだけのことがある。
- **V は段階にほとんど効かない**: 同梱の一覧を 6・8・12・16・24 GB の NVIDIA で判定し、V と V_tile を 0 にすると
  段階が変わるのは延べ 13 件(1,625 件のうち。0.11.0。MOSS Image 4・音声 3・Qwen Image 2.1 の 2・SDXL の 2 つのワークフロー・VOID 2)。
  載せたままの量(#102)で変わるのは 8〜32 GB の 1,625 件で 16 件で、段階が下がるのは 2 件(32 GB の Kandinsky 5 の 2 つ、
  Perfect → Good)。ほかは Good のまま動かし方が GPU から GPU~ に替わるだけ。
- そのため SDXL の全部載せは 512px から 2000px ほどまで同じ値になる(一番重い段がタイルの VAE の 1.06 GB で、
  生成の段は 1024px でも 0.26 GB)。それより大きいと生成の段が効いて増える。
  ほとんどのモデルでは重みか生成の段が先に効く。V の主な効き目は、全部載せを選べるか(載せたままの量)と、V が VRAM を超えるときの「タイルに分ける(遅い)」の注意。

### 系統の当て方

`comfy_family` / `comfy_vae`(`families.py`。docs/hardware「系統の表」)と本体の大きさで、`working.py` の表の行を決めます。

- **大きさは本体のファイルの `header_params`**(safetensors / GGUF の見出しの要素数。無ければ一覧の `params_b`)の区分で決める
  (dim・hidden_size は読まない。キャッシュ・スキーマを変えず、決まった値になる):
  - Wan: 2.5B 未満 → dim 1536、7B 未満 → 3072(Wan 2.2 5B)、それ以上 → 5120。係数 = dim / 2222(supported_models.py:1374)。
    VACE は × 1.2(:1456)、WanDancer は 1.8(:1590)
  - Flux2: 6B 未満 → hidden 3072(Klein 4B)、12B 未満 → 4096(Klein 9B)、それ以上 → 6144(dev 32B)。係数 = 3.1 × 4 × hidden / 2604(:820)
  - LTX: 14B 以上 → LTXAV(LTX-2 / 2.3。係数 0.077、:980)、10B 以上 → LTXV 13B(11 = 5.5 × 4096 / 2048、:960)、ほか → LTXV(5.5)
  - SD: 本体(全部入り)が 3.3B 以上 → SDXL(0.8、:219)、未満 → SD1.5・SD2・SDXL refiner(どれも 1.0、:69・116・180)
- そのほかの係数: SD3 1.6・Flux 3.1・Chroma 3.2・LongCat 2.5・HiDream 2.0(既定)・Lumina2 1.4・Z-Image 2.8・
  Omnigen2 1.95(Boogu 2.15)・Kandinsky5 1.25・Krea2 2.2・Qwen Image 1.8・JoyImage 1.8・Anima 0.95・Lens 4.0・
  Ideogram4 11.6・MOSS-Image 14.6・ERNIE 10.0・MageFlow 6.5・Qwen Image 2.1 6.0・HiDream O1 0.033・PixelDiT 0.04・
  HunyuanVideo 1.8・HunyuanVideo 1.5 4.0・CogVideoX 2.0(既定)・MiniMax H3 0.114・ACE-Step 1.5 4.7・ACE-Step 1 0.5・
  Stable Audio Open 2.0(既定)・YuE2 4.0(出典の行は `working.WORKS`)。
- VAE(#100 で分けた): `wan22`(Wan 2.2 5B、16 倍圧縮)・`qwen21`(Qwen Image 2.1、16 倍圧縮)・`flux2`(Flux2 の VAE × 4)・

同梱の一覧(329 件)で 86 件:

当てられる系統を増やすのは宿題(下の「分かっている限界」)。

**作業用メモリ(当てられないモデル)**:

- 画像 = 係数 × メガ画素 × 枚数
- 動画 = 係数 × メガ画素 × (コマ数 / 49)^0.5 × 枚数
- 音声 = 係数 × 分
- 3D = 一定
- 係数は 0.10 で合わせた値のまま(#100 から合わせ直すのは 3D だけ。下の「合わせ方」)。
- 動画の指数 0.5 は合わせていない(実測が 1 件しかない)。指数の値そのものは根拠のある数字ではない。

**精度の指定**(`Settings.precision`、CLI の `--precision`):

- 本体の重みだけを換算する(例: bf16 → fp8 で半分)。
- 大文字・小文字や書き方の違い(`BF16`、`float16`、`gguf-Q4_K_M`)はそろえてから比べる。
- 元の精度は `ModelEntry.precision`、無ければ本体のファイル名(`bf16` / `fp8` / `int8` など)から読む。
- 分からなければ換算しない。

**段階**(2026-10-20 から。llmfit の docs/how-it-works.md「Fit analysis」にならう):

- 動かし方で使う置き場所(GPU なら VRAM、CPU ならメインメモリ)の使用率で決める。
  - 60% 以下 Perfect
  - 85% 以下 Good
  - 98% 以下 Marginal
  - それより上 Too tight
- 動かし方ごとの上限:
  - 全部 GPU は上限なし。
  - 順に載せ替える(GPU~)と逃がす(GPU+RAM)は Good まで(逃がすのは 0.10 まで Marginal まで)。
  - CPU は、生成が Marginal まで、CPU で実時間に動く設計の読み上げ・1 回の計算の道具が Good まで(0.11.0、#108)。
  - GPU の会社による上限は無い(0.10 まで、NVIDIA 以外と DGX Spark は Good まで)。
  - 決まりの全体は [scoring.ja.md](scoring.ja.md)「段階の上限」。
- 一番良い段階の動かし方を取る(同じなら逃がさない)。メインメモリの確かめ(下の「メインメモリ」)はそのあと。
- 大きさが分からなければ段階を付けない(`unknown`、表では `?`。下の「大きさが分からないモデル」)。
- 以前は「全部載せが VRAM の 90% 以内なら Perfect、VRAM 以内なら Good」だった。
- 同梱の一覧での変わり方(段階を変えた時点の一覧の全 341 件。HF の下限を上げる前。0.9.1 の同梱の一覧(2026-10-21)は 329 件):
  - 8 GB / 32 GB: Perfect 44 → 23、Good 22 → 32、Marginal 87 → 97、Too tight 188 → 189。
  - 16 GB / 32 GB: Perfect 95 → 66、Good 67 → 76、Marginal 107 → 124、Too tight 72 → 75。
- AI生成キットの推奨の VRAM(8 GB)では、Z-Image Turbo int8 は順に載せ替えると使用率 94% なので、0.11.0(#108)から
  重みの一部を逃がして Good(GPU+RAM。遅い。それまでは順に載せ替えて Marginal)。
  Wan 2.1 1.3B も同じ(順に載せ替えて 97% → 逃がして Good)。tests/test_estimate.py。
- 逃がしても GPU に載らないときは、GPU が無いときの判定(小さく CPU で動く種類なら Marginal)とも比べて良いほうを取る。
  - 小さな GPU を足すと、CPU で動くものまで動かない判定になり、VRAM を増やして段階が下がっていた(#17)。

### メインメモリ

- GPU に載せて動くとき(全部載せ・順に載せ替え)は、**固定分 3.0 + いちばん大きい段の重み**とした。
  - 根拠は**仮定**: ComfyUI は safetensors をメモリに割り当てて(mmap)読み、部品を 1 つずつ GPU へ送る。
    だから使い終わった部品のページは OS が捨てられる。
  - 実測は無い。
- 逃がすとき・CPU のときは、逃がした重みがメインメモリに居続けるので、固定分 + 全部品(安全側)。
- 足りないときの扱い:
  - 必要量が搭載量の **1.5 倍まで** なら Marginal。足りない分は仮想メモリ(ページファイル)を使うので遅い。理由に出す。
  - 超えたら Too tight。
- 1.5 倍にした経緯:
  - Windows の既定(システム管理)のページファイルは、搭載量と同程度以上まで伸びる。
  - ただし重みをページファイルに置くと極端に遅くなるので、半分までにとどめた。
  - **1.5 は判断で決めた値で、実測していない**。
- ページファイルの大きさが決まっている PC(固定の大きさ・ページファイル無し・Linux のスワップ)では、
  上限を「搭載量 + その大きさ」(ただし 1.5 倍まで)にする(#21。[hardware.ja.md](hardware.ja.md)「メモリと仮想メモリ」)。
- 以前は「3 GB + 全重み、足りなければ Too tight」だった。
  - これだと AI生成キットのカタログの最低メモリ 16 GB と食い違った。
  - 16 GB の PC では GPU に関係なく Wan2.2 5B(重み 16.9 GiB)が Too tight になっていた。
  - 今は 8 モデルとも、16 GB(と 15.3 GiB と出るノート PC)で、メモリを理由に Too tight にならない(`tests/test_estimate.py` が検査)。

### 大きさが分からないモデル

次の条件がそろうと、重みを 0 として「載る」とは言いません。

- ファイルの大きさが無い(None・0・負)ものが 1 つでもある。
- テンプレートの大きさも、パラメータ数 × 精度も無い。

そのときの出力:

- `fit = "unknown"`・`run_mode = "unknown"`・`basis = "estimated"`・`unknown_size = true`(`fit` は 0.1.1 より前は `too_tight`、`run_mode` は 0.2.0 より前は `none`)
- 理由の先頭に「大きさが分からないため判定できません」を出す。
- `recommend` からは外す(`fit --fit all`・`search`・`info` には出す)。
- VRAM・メモリの値は JSON では null(Python の属性は 0.0 のまま)、`limits` は null。
- GPU が無いときも「小さいので CPU で動く」とは見ない。

## ファイルの数え方(#2 との約束)

#2 の一覧には、部品ごとに 1 つの版(1 つの精度、なるべく .safetensors、単一ファイルと diffusers 形式の片方)だけを入れます。
それでも Hugging Face のリポジトリの並びをそのまま渡されたときに大きく数えすぎないよう、
見積もりの側でも次の決まりで数えます(`estimate.select_files`)。

1. **数えないファイル**
   - 重みでないファイル(`.json` `.txt` `.md` 画像など)
   - ComfyUI で使わない形式(`onnx/` `flax` `openvino` `safety_checker/`、`.onnx` `.msgpack` `.h5` など)
2. **部品ごとに 1 組だけ**数える。部品の決め方:
   - ComfyUI の置き場所 + 名前(精度・形式・分割番号を除いたもの)
     - `t5xxl_fp16` と `t5xxl_fp8_e4m3fn` は同じ部品。
     - `clip_l` と `t5xxl` は別の部品。
   - HF の diffusers のフォルダ
     - 中の `model` / `pytorch_model` / `diffusion_pytorch_model` は 1 つの部品。
     - VAE のフォルダは `vae` と `vae_1_0` などを 1 つにする。
   - フォルダの外の本体(名前が同じか、一方が他方で始まるもの)
     - `sd_xl_base_1.0` と `sd_xl_base_1.0_0.9vae` は同じ部品。
     - 高ノイズ用と低ノイズ用のように名前の違う本体は別の部品。
3. **1 組の選び方**:
   - 形式: `.safetensors` > `.gguf` > `.bin` / `.ckpt` / `.pt(h)`
   - 次に精度: fp16 / bf16 > 精度の書いていないもの > fp8 / int8 / q8 > q6 > q5 > q4 / nf4 > fp32
   - 同じなら大きいほう(安全側)
   - 分割(`-00001-of-00003`)は全部数える
4. **単一ファイルと diffusers 形式の両方があるとき**は、単一ファイルを数える。
   - 単一ファイルが全部入りと分かっている(SDXL など、内訳表にあるもの)ときは、diffusers のフォルダを全部除く。
   - 分からないときは、フォルダの外に同じ役割(本体・VAE)のファイルがある diffusers のフォルダだけ除く。
     - 単一ファイルが本体だけ(FLUX の `flux1-dev.safetensors` など)のときに、エンコーダを数え落とさないため。
     - 全部入りなのに内訳表に無いときは、多めに出る(安全側)。
   - **依頼の文面は「単一ファイルだけ数える」だったが、本体だけの単一ファイルでエンコーダ(FLUX なら T5 の約 9 GiB)を数え落とすので、こうした**。
5. 除いたファイルがあれば理由(`reasons`)に出す。`disk_gb` は数えたファイルの合計。
6. **任意の部品**(#81、0.12.0。公式テンプレートの既定の値で読み込まれない部品。決め方は
   [sources.ja.md](sources.ja.md)「任意の部品」):
   - `inactive`(無効・素通しのノードや、どの出力のノードにも届かないノードにしかない部品)は、VRAM・メインメモリ・
     `disk_gb`・`download` のどれにも数えない。
   - `switch_off`(値の決まったスイッチの選ばれない枝にしかない部品。指示の書き直し・高速化の LoRA など)は、
     VRAM・メインメモリに数えない。ComfyUI の検証は選ばれない枝のファイルも確かめるので、`disk_gb` と `download` には数える。
   - スイッチを全部入れたときの上限(`vram_gb_all_options`・`fit_all_options`)も出し、段階が変わるときだけ
     理由に 1 文を出す([scoring.ja.md](scoring.ja.md)「既定で切ってある部品」)。
   - 実測は既定の値で測ったものなので、ずらし(下の「実測の使い方」)は既定で読み込む部品で決める。

## 実測の使い方

RTX 5080 の実測は ComfyUI の動的 VRAM で測ったもので、**空きがあれば多めに使います**。
16GB で 13.2GB(Z-Image int8)は必要量の下限ではありません。そこで次のように使います。

1. 実測は「全部載せ」(`vram_gb`)の値として使う。
   - 「実測 − 式の値」(d)だけ作業用メモリをずらす。式の値は、実測の設定での段ごとの式(VAE はタイルの値 V_eff)。
   - **負のずらし**は、全部載せ・順に載せ替え・逃がすの各段の作業用メモリに足し、段ごとに 0 で切る(#100)。
     どの量も重み + 固定分(作業用メモリ 0)の下限を下回らない(#95 の下限)。
   - **正のずらしは全部載せにだけ足す**(段ごとに当てられるモデルも、当てられないモデルも)。張り付いていない実測が
     式より大きいのは、余裕のある GPU で動的 VRAM が部品を載せたままにし、VAE もタイルに分けずに仕上げた山だから
     (Wan 2.1 1.3B の +1.96 GB は、タイルなしの V 3.42 GB とタイルの V 0.27 GB の差でほぼ説明できる)。
     順に載せ替え・逃がすでは起きない量。
   - **GPU の上限に張り付いた実測**(これ以上としてだけ使う)からのずらしは 3 つに足す。
     どちらにするかは実測で決まるので、判定する PC の VRAM について単調。
   - v3 の「3 つに同じずらし」(`max(a + d, b + d) = max(a, b) + d`)が成り立つのは、ずらしが固定分の誤差のときだけ。
     ほかの理由(動的 VRAM が空きを使った・タイルに分けなかった)の差は段ごとに違うので、上の決まりにした。
   - 実測(メンテナ・ほかの利用者とも)が下限を下回ったら下限まで上げる(重みの一部をメインメモリに置いていた実測)。
     差が 0.1 GB 以内なら丸め・測りの揺れとして `basis: "measured"` のまま値は下限にし、理由に出す
     (ACE-Step 1.5 の 10.80 GB と下限 10.82 GB の 0.02 GB。`estimate.MEASURED_FLOOR_TOLERANCE`)。
   - 小さい GPU では、全部載せが入らなくても**順に載せ替え・逃がすへ落ちる**。
     例: 8GB で Z-Image int8 は全部載せ 13.2 GB だが、順に載せ替えて 7.5 GB で動く。使用率 94%(Marginal)なので、0.11.0 からは代わりに重みの一部を逃がし、段階は Good(GPU+RAM)。
   - 実測の値が GPU より大きいことだけでは Too tight にならない。
2. 実測が GPU の容量の 90% 以上(または offload が lowvram など)なら「上限に張り付いた」とみなす。
   - **下限としてだけ使う**(全部載せ = max(式, 実測))。
   - 該当は Z-Image bf16(15.0 / 16)と Wan2.2 5B の 2 件(15.8 / 15.0)。
3. 設定(解像度・コマ数・長さ・**枚数**・精度)が実測と同じときだけ `basis: "measured"`。
   - 精度は書き方をそろえる。実測に精度の記録が無ければ、モデルの元の精度とみなして比べる。
   - 違う設定は、実測でずらした推定で `basis: "estimated"`(理由に「…の実測で補正した推定」と出す)。
   - 精度を変えたら実測は使わない。
4. 設定を指定しないとき(0.11.0 で変えた。[scoring.ja.md](scoring.ja.md)「判定に使う設定」):
   - 実測の有無によらず、どのモデルも種類ごとの既定(画像 1024px、動画 832x480・81 コマ、音楽 30 秒など)で判定する。
   - 実測の設定は、作業用メモリをずらす量を計算するときだけ使う。メンテナの画像・動画・音楽の実測(AI生成キットの「はやい」画質:
     768〜832px・512〜640px の動画・20 秒の音楽)は既定と合わないので、既定の設定では `calibrated`(表に `m` が付かない)。
   - 0.10 までは、実測のあるモデルは実測の設定で判定していた(メンテナの測ったモデルだけ小さな設定で比べることになっていた)。
   - 実測の設定で判定したいときは `--width` などを指定する(アプリは `judge_model(..., settings=...)`)。
   - 大きさの入力の無いテンプレート(入力の画像から作る深度推定・背景除去など)は、判定の設定に大きさを持たない(#90)。
     - どのテンプレートに大きさの入力が無いかは、メンテナが確かめた手の表(`estimate.NO_SIZE_INPUT`。根拠は bench の記録かテンプレートのノード)だけで決める。ほかの利用者の提出では決めない(1 件の提出で、大きさの入力のあるモデルの判定をどの PC でも変えないため)。
     - 新しいテンプレートは、最初の bench の記録を見て足す(bench は大きさの入力があるときだけ実測に幅・高さを書く。表に無いモデルの大きさの無い提出には、PR で `settings_missing` の注意が出るので、メンテナが気づける)。
     - 大きさの無い実測が、指定の無い判定と同じ設定になる。`--width` などを指定したときは今までどおり。
     - 作業用メモリは今までどおり種類の既定の大きさ(画像 1024px など)で見積もる。
5. GPU が無い(`--vram 0` など)ときは、GPU の実測を使わず `basis: "estimated"`・`measured_on: null`。
6. 次の実測は、見積もりにも合わせ直しにも使わない(#5 の bench が書く)。
   - `outcome` が `ok` でないもの(OOM・エラー)
   - `standard: false` のもの(独自のワークフローや追加の上書き)
7. **作業用メモリだけの実測**(#100): `vram_metric` が `torch_reserved` で `offload` が `dynamic` の実測
   (bench が動的 VRAM で測ったもの)は、重みを含まない(動的 VRAM は重みを要るときに読み込み・追い出す)。
   - 段ごとの山を測れるようになるまで、**段階にもずらしにも使わず、照合(下)だけに使う**(`estimate.working_only`)。
   - 同梱の RTX 5080 の 9 件(`vram_metric` が null)は今までどおり全体の量。
   - ほかの利用者の提出(bench の結果)も同じ。まとめて残すが、見積もりは動かさない([schema.ja.md](schema.ja.md)「contrib」)。
8. 実測の値は GiB とみなす(`measurements.json` の `unit`)。
   - AI生成キットの記録に単位の明記は無い。
   - ComfyUI と nvidia-smi が MiB で数えることからの**仮定**。

## 合わせ方

- **#100 から合わせるのは `act_3d_gb`(3D の作業用メモリ)だけ**。実測は 3D の 2 件。
  - 段ごとに当てられるモデルの作業用メモリは ComfyUI の見込みで、係数を持たない(実測に合わせない)。
  - 当てられないモデルの画像・動画・音声の係数(`act_image_gb_per_mp` / `act_video_gb_per_mp` / `act_audio_gb_per_min`)と
    固定分 `overhead_gb` は、0.10 で 9 件に合わせた値に固定する(`calibrate.FROZEN`。calibration.json の `frozen`)。
  - 固定分は RTX 3070 を測り直してから決め直す(下の「照合」)。
- 固定のもの: 重みの係数(1.0)・逃がす割合(0.4)・動画の指数(0.5)・メインメモリの固定分(3.0)・メモリの倍率(1.5)。
- 使う実測は同梱のもの(`measurements.json`・`measurements_community.json`)だけ。この PC の bench の実測(キャッシュ)は除き、
  除いた件数を出す(どの PC で作っても calibration.json が同じになる。#100)。
- 最小にするのは次の合計(3D の 2 件):
  - **相対誤差の 2 乗和**(張り付いた実測は、予測が下回ったときだけ数える片側の 2 乗)
  - 事前値(#1 の仮の値)からの相対的なずれへの弱い罰(重み 1e-4)
- 精度は leave-one-out で測る。合わせない行(3D 以外)は、全件の予測と LOO の予測が同じになる(式に実測を使っていない)。
- 目標の判定(`target_met`)は、張り付いていない実測が 2 件以上ある種類だけで行う。

**人が決めた目安との関係(正直に書く)**:

- AI生成キットのカタログの最低 / 推奨 VRAM は、式にも係数にも使っていない。
- ただし **逃がす割合 0.4 は、目安を見て選んだハイパーパラメータ**。
  - 実測で決められないので、「SDXL が 4GB で動く」「bf16 の Z-Image が 4GB では動かない」の 2 つと矛盾しない範囲から選んだ。

## 分かっている限界

- **GPU が 1 種類だけ**: 合わせ・照合に使う全体の量の実測 9 件は、どれも RTX 5080 16GB・動的 VRAM。
  - 小さい GPU での「順に載せ替え」「逃がす」の値は検証していない。
- **動的 VRAM**: 空きがあれば多めに使うので、実測は「必要量」ではなく「その GPU で使った量」。
  #100 から、正のずらし(Wan 2.1 1.3B で +1.96 GB)は全部載せにだけ足す(上の「実測の使い方」1)。
- **張り付いた実測**: Z-Image bf16 と Wan2.2 5B の全部載せの値は式だけで決まっていて、実測では上から押さえられていない。
- **Wan の縦横比**: 動画の実測は長辺(512px / 640px)しか記録が無く、正方形と仮定した。
- **日付が不明**: 実測の日付・ComfyUI の版の記録が無い(measurements.json の date が空)。
- **単位**: 実測は GiB と仮定した(上の「実測の使い方」8)。
- **メインメモリ**: 式も 1.5 倍も実測で確かめていない(上の「メインメモリ」)。
- **NVIDIA 以外の GPU**(0.7.0、#22): AMD・Intel・Apple の実測は 0 件。
  - 段ごとの作業用メモリは SDPA の式のまま(分割式の GPU では理由に注意を出すだけ)。AMD は KL の VAE を × 2.73。
  - この種類の GPU で動いた実測がまだ無い。0.11.0 より前は段階を Good までにしていた(2026-10-22)。0.11.0(#108)で上限をやめ、確認済みの種類の印(✓)を付けないことで示す。
  - GPU のメモリとみなす割合は、一次資料の挙動から決めた目安で、実測していない([hardware.ja.md](hardware.ja.md)「共有メモリ」)。
- **CPU で動く系統**(#39): SD 系・Stable Audio の CPU のメインメモリは、ComfyUI のコードから決めた式で、実測していない。
  - 式は、本体・VAE を fp32 に広げ、作業用メモリ × 2(段ごとの式では一番重い段 × 2)。
- **分かっている外れ**(人が決めた目安との突き合わせ、`tests/test_estimate.py` が strict な xfail で記録):
  - 今は外れ無し: 8 モデルとも、目安の最低 VRAM で Too tight にならず、推奨 VRAM で GPU で動く。
  - Wan2.2 5B の外れ(#100 より前は 8GB で Too tight)は、段ごとの式(Wan 2.2 の VAE の見込み)で直った。
  - Wan 2.1 1.3B は、アプリの設定(512px・49 コマ)で 6GB も 8GB も逃がして Good(8GB で順に載せ替えると使用率 97%。0.11.0 より前は Marginal)。
- **宿題**(#100):
  1. 文章の読み取りの作業用メモリ: Qwen2.5-VL の画像のトークン、Flux2 の Mistral、YuE2 の楽譜の段(8192 トークン)、
     ACE-Step 1.5 の LM の KV など、ComfyUI が見込まないもの
  2. 段ごとの山を bench で測る(段の境目で区切る)。作業用メモリだけの実測(上の「実測の使い方」7)を使えるようにする
  3. 当てられないモデル(86 件)を減らす(Flux3 の大きさ、Stable Audio 3 の VAE、SeedVR2・Ming の VAE など)

     Wan 14B fp8 が 12 GB で動く報告と合わない原因
  6. Klein 9B・Flux3 Klein の 6 GB、Z-Image bf16 の 16 GB(順に載せ替えの使用率 0.864)など、境目の判定の実測
  7. CPU のときの作業用メモリ(メインメモリで 2 倍する分)の中身
- **全部入りの内訳を知らないモデル**(#2 で増える HF のものなど)は一般的な割合で分けており、順に載せ替え・逃がすの値の誤差は大きい。

  一覧に無いテキストエンコーダは本体として数える(全部載せの値は変わらないが、順に載せ替え・逃がすの値は大きめに出る)。

## ほかの利用者の実測(#34、2026-10-21。扱いは 2026-10-22 に llmfit に合わせた)

利用者が `genmodelfit bench --submission` で作った提出用の JSON を、Pull Request で `data/contrib/<GPU>/<日付>-<sha8>.json` に足してもらいます
(手順は [CONTRIBUTING.ja.md](../CONTRIBUTING.ja.md)、形は [schema.ja.md](schema.ja.md)「contrib」)。
**2026-10-29 時点で受け付けた提出は、1 つの出どころ(メンテナ)の 4 件**です(#126。RTX 3070 の SDXL の 4 つの設定)。
同梱の `src/genmodelfit/data/measurements_community.json` は 4 行(それぞれ提出 1 件)で、そろった(consistent)行は
まだありません(出どころが 2 つ以上要る)。だから係数の合わせ直しにはどれも入りません。
下の決まりは、提出の扱いです。

**測ったファイルの違い(#90)**: ほかの利用者の提出(contrib_schema 2)とこの PC の bench の実測には、測った時点の一覧のファイルの指紋 `files_fp` が入り、毎週の一覧の更新で上流のファイルが変わる(指紋が違う)と使われなくなります。メンテナの実測(`measurements.json`)には指紋が無いので、ファイルが変わっても今までどおり使います(メンテナの実測はメンテナが測り直す。ほかの利用者の行は黙って使われなくなり、メンテナの行は使われ続ける、という違いがある)。使われなくなった同梱の行は `genmodelfit contrib aggregate --check` が出します。

**2026-10-22 のメンテナの決定**: llmfit(main、2026-10-22 に読んだ)と同じ考え方にする。

- llmfit のやり方:
  - 提出(`llmfit bench --share` の PR)を CI で機械的に検査するだけ。
    - 検査するもの: schema・パスと名前・大きさ・時刻・値の上限・min ≤ avg ≤ max。
    - 署名も人の確認の仕組みも無く、マージがメンテナの確認になる。
  - 同じ CPU 名・GPU 名の実測だけを中央値でまとめ、件数(sample_count)を持つ。
  - 1 件でも使い、推定を両方の向きに上書きする。
  - 優先は 自分の実測 > 同じハードのほかの利用者の実測 > 推定。
  - ほかのモデルへの補正は、実測 ÷ 推定 の中央値を [0.05, 3.0] に収める。
- 2026-10-21 の決まりは外した。
  - 内容: 必要量を上げる向きにだけ使う・+15% まで・2 件以上でばらつき 15% 以内・人が sha8 ごとに確かめた提出だけ。
  - 理由: メンテナに分かりにくかった。実測が来ても NVIDIA 以外の GPU の当時の「Good まで」の上限(0.11.0 の #108 でやめた)を外せなかった。

**まとめ方**(`genmodelfit contrib aggregate`):

- 次が同じものごとにまとめる。
  - モデル
  - GPU(PCI の型番 ID があれば ID、無ければ `gpu_slug` でそろえた名前)
  - GPU の VRAM(1 GB に丸める)
  - 測り方(`vram_metric`)
  - 設定(解像度・コマ数・長さ・ステップ数・精度・枚数)
- 標準でない提出(`standard: false`)は使わない。
- 最後まで動いた(ok)ものの最大 VRAM を使う。
  - 3 件以上あれば、|x − 中央値| / (1.4826 × MAD) > 3.5 を外れ値として除く(MAD の下限は中央値の 2%)。
  - 残りの中央値を値にする。
- 件数(`n_used`)と、同じ構成で OOM だった件数(`n_oom`)を持つ。
- ok と OOM が混ざる組は ok の中央値を使い、OOM の件数を理由に出す。
- OOM だけの組は `outcome: oom` の 1 行(見積もりには使わない)。

**使う条件**: **この PC と同じ GPU** の実測だけを、この PC の必要量・段階に使います。

- llmfit と同じ(0.9.0)。別の GPU・GPU の無い PC の判定は、ほかの利用者の実測があっても無くても同じ。
- 同じ GPU かは `estimate.same_gpu` で決める。
  - 両方に PCI の型番 ID(`1002:744c`)があれば ID。
  - 無ければ `estimate.gpu_key` でそろえた名前((R)・(TM)・™・®・大小・空白・NVIDIA / GeForce の語を除く)。
- **加えて VRAM が近いこと**(0.9.1。`estimate.same_vram`):
  - 実測の GPU の VRAM と この PC の総量の比(小さい ÷ 大きい)が 0.95 以上(0.11.0。0.9.1〜0.10 は 0.97)。
  - 同じ名前・同じ型番 ID でも VRAM の違う GPU があるため(RTX 4060 Ti の 8 / 16 GB、RTX 3060 の 8 / 12 GB、PCI ID `744c` の RX 7900 XT・XTX・GRE)。
  - 0.95 は、同じカードの OS・ドライバによる総量の数え方の違い(`MEASURED_VRAM_TOLERANCE`)を許す幅。Linux の CUDA は予約の分を引いた総量を報告する: 6 GB のカードで 5.80 GiB(5934 MiB。NVIDIA の開発者フォーラムの RTX 2060 の報告)、8 GB で 7.79、10 GB で 9.78、11 GB で 10.76、12 GB で 11.77、24 GB で 23.69。Windows は 6.0・7.99・15.92 など。6 GB の 5.80 ÷ 6.0 = 0.967 は 0.97 に届かず、同じカードの Linux と Windows の持ち主が別の GPU になっていたので、0.95 にした。
  - VRAM の違う版の比は 0.83 以下(RTX 3080 の 10 / 12 GB など)なので、間に余裕がある。
  - 内蔵 GPU・APU・Apple(共有・統合メモリ。総量が PC のメインメモリで決まる)は比べない。
- ほかの利用者の実測の点検(`contrib` の fit_change)は、名前の表で公称の VRAM が分かる GPU ではその VRAM の PC でも行う。
  - 対象: Intel Arc と、NVIDIA の `estimate.NVIDIA_VRAM_VARIANTS`(RTX 2060・3050・3060・3080・4060 Ti・5060 Ti)。
  - NVIDIA の公式の製品ページで確認。出典は定数のコメント。
  - ノート用 GPU・GTX 16 系は、VRAM 違いが無い・名前が別なので表に無い。
- 「AMD Radeon(TM) Graphics」「Intel(R) Arc(TM) Graphics」のような汎用の名前は、世代の違う GPU が同じ名前になるので、名前では一致させない。
- メンテナの同梱の実測は、値をずらすのにはどの PC にも使う(今までどおり)。段階を決めるのは同じ GPU だけ(0.11.0。下の「段階」)。
- ok の行は、値をずらすのには **1 件から**使う。`consistent`(出どころ 2 つ以上・幅 15% 以内・OOM なし)は、係数の合わせ直しに入れる条件で、段階を決める条件にも使う(0.11.0)。

**向き**: 必要量を**下げる向きにも上げる向きにも**使います。点数もメンテナの実測と同じに数えます。抑えるのは物理的な範囲だけです(`estimate._prepare`)。

- 下限: 全部載せの値は**重み + 固定分**(作業用メモリ 0)より下げない。
  - それより小さい実測は、一部の重みをメインメモリに置いていた(動的 VRAM・partial)か、測り違い。
  - 見積もりは下限の値にする。`basis` は estimated(`basis_detail` は calibrated。0.11.0 より前は measured_community)。理由に「下限の値にした」と書く。
  - 以前 validate が要確認にしていた条件(`offload: none` で重み + 固定分より小さい)を、見積もりでの切り詰めにした。
- 上限: 測った GPU の総量 × 1.02 + 0.25 GiB(validate の「ありえない値」と同じ)。
  - 超えた値はこの上限(総量 × 1.02 + 0.25 GiB)までにする(`estimate._prepare`)。
  - 理由には「GPU の総量を超えるので、上限(総量 × 1.02 + 0.25 GB)までにした」と出る。
- メインメモリの最大(`peak_ram_gb`)は、提出のメインメモリ × 1.05 + 1 GiB までにする(読むときに切り詰める)。
- GPU の上限に張り付いた実測(総量の 90% 以上・lowvram)は、メンテナの実測と同じく「これ以上」としてだけ使う。
- 設定の違う推定へ広げる(calibrated)ときは、実測 ÷ 式 を **[0.6, 1.4]** に収める(llmfit の [0.05, 3.0] に当たる)。
  - 範囲は、validate が「式から外れている」と知らせる幅(±40%)と同じにした。
  - メンテナの実測の 実測 ÷ 式 は 0.64〜1.03(張り付いた Z-Image bf16・Wan2.2 5B が 0.64〜0.72、ほかは 0.98〜1.03)。
    VRAM は速さ(llmfit が補正する量)より式に近い。
  - 下側は重み + 固定分の下限のほうが先に効くことが多い(メンテナの実測で下限 ÷ 式 は 0.73〜1.0)。
- 判定する既定の設定は、ほかの利用者の実測の設定に変えない(小さな設定の提出で既定の設定そのものを小さくしない)。
- メンテナ・この PC の `torch_reserved` の実測(CUDA の文脈を含まない。RTX 3070 の 2 件)は、これまでどおり「これ以上」としてだけ使う。
- ほかの利用者の `torch_reserved` の実測は、下限(重み + 固定分)まで下げてよい。bench の提出はすべて torch_reserved なので、下げる向きに使えなくなるため。

**実測の選び方**(`estimate.pick_measurement`): ほかの利用者の実測は同じ GPU のものだけが候補です。次の順で選びます。

1. 設定が同じもの
2. **この PC と同じ GPU の実測**
3. メンテナ・この PC の実測
4. ほかの利用者の実測
5. 張り付いていないもの
6. 大きい GPU
7. 大きい値

GPU 名は `NVIDIA` / `GeForce` の有無・大文字小文字・記号をそろえて比べます(`estimate.gpu_key` = `contrib.gpu_slug`)。

**段階**(#26 の「実測で段階を決める」、`estimate.measured_level`。0.11.0 で条件を変えた。決まりの全体は [scoring.ja.md](scoring.ja.md)「実測で段階を決める条件」):

- この PC と**同じ GPU**(`estimate.same_gpu`)の、同じ設定で成功した実測だけを段階の根拠にする。メンテナの実測もほかの利用者の実測も同じ規則(似た GPU には広げない。0.10 までは、メンテナの実測は同じ会社で VRAM が実測の GPU 以上ならどの GPU にも効いた)。
- **別々の出どころが 2 つ以上**そろったときだけ決める。メンテナの実測は何行あっても合わせて 1 つ(メンテナだけでは決めない)、ほかの利用者はまとめの `n_sources`(提出を送った人ごと。何回の Issue・Pull Request で送っても 1 人で 1 つ。#113)。足して数える。1 つだけなら値をずらすだけ。
- そろう: OOM の記録が無い(同じ構成の `outcome: oom`・`n_oom`・`runs_evidence: false` が無い)、まとめの中もそろっている(`consistent`)、行どうしの幅が中央値の 15% 以内。
- **段階に使う量 = max(一番大きいピーク + 文脈の分, 重み + 固定分)**。表の VRAM と同じ値(`measured_level_vram_gb`)。作り物の小さな値で段階が跳ねないように、値の欄と同じ物理的な下限を使う。
  - この量がこの PC の VRAM に収まらなければ決めない(例: Wan2.2 5B は重み + 固定分が約 18.4 GB で、RTX 5080 の 15.9 GB に収まらない)。
  - Perfect は 60% 以内。張り付いた実測があれば Perfect の根拠にしない(Good まで)。
- `torch_reserved` は、文脈の分 0.5 GiB を足した値で帯を決め、Perfect の根拠にもする(0.9.0)。
- 実測は段階を上げるだけで、下げない(0.11.0 から NVIDIA 以外の GPU も同じ。NVIDIA 以外の「Good まで」の上限は #108 でやめた)。

**根拠の段階**(`Estimate.basis_detail`)と出どころの数(`Estimate.sample_count`。0.11.0 で提出の件数から変えた):

- `basis` は後方互換のため measured / estimated の 2 値のまま。
- `sample_count` は JSON に足しただけ。
- 表示:
  - `info`: `measured n=3`
  - 表の VRAM の印: `m`(メンテナの実測と同じ。0.11.0 で `c` をやめた。#108)
  - 理由: 「ほかの利用者の実測(出どころ 3。中央値 7.02 GB)」

| 段階 | basis | 意味 |
|---|---|---|
| `measured` | measured | 設定が同じ実測(同梱のメンテナの実測・この PC で bench が保存した実測・ほかの利用者の実測(1 件から)を分けない。0.11.0 で measured_community をまとめた) |
| `calibrated` | estimated | 設定の違う実測(メンテナ・ほかの利用者)でずらした推定。設定が同じでも下限・上限で切り詰めた値 |
| `estimated` | estimated | 式だけの推定(実測が無い・精度を変えた・GPU が無い) |

**検査**(`contrib validate`、CI の contrib.yml): **機械的な検査だけを失敗にする**。

- 失敗にするもの:
  - 形・値の範囲・個人の情報・重複・ファイル名・大きさ
  - 値の範囲は、GPU の VRAM 256 GiB 以下、最大メモリはメインメモリ × 1.05 + 1 GiB 以下、NaN・無限大・負の数は不可(0.9.0)。
  - GPU 名と `system.gpu.vendor` の会社が違うもの
  - `pci_id` の形・会社が違うもの
  - `hardware.PCI_DEVICE_NAMES` の GPU と名前が合わないもの(表に無い ID は確認)
- 「確認」(notices)として、ジョブのまとめの上に出すだけにするもの:
  - 式から 40% より外れる(`deviation`)
  - 全部載せ(`offload: none`)なのに重み + 固定分より小さい(`below_weights`)
  - 提出と同じ GPU(名前・型番 ID・会社、VRAM は提出の `vram_gb`)× メモリ 16 / 32 / 64 GB の PC で段階を変える(`fit_change`。同じ GPU で段階が上がるのも出す)
  - 一覧に無いモデル
  - 表に無い GPU
- 人が sha8 ごとに確かめる仕組み(`--allow-review`・`data/contrib/REVIEWED`)は外した。
- contrib.yml の安全の仕組みは残す。
  - pull_request で動く。
  - 検査は PR の向き先のコードで行う。
  - data/contrib の外を変えた PR は失敗にする。
  - 提出の文字をログに出さない。

**残る危険**:

- 書き換えた提出は、マージされればそのまま見積もりと段階を動かす。
  - 2026-10-21 のレビューで見つけた類い: 小さな値の提出で必要量を最大 76% 下げる、+39% の提出で段階を下げる。
  - これらは下限・上限の内側では防がない。
- 防ぐのは**マージする人の確認**。そのために確認(notices)と、`contrib aggregate --report` の「ほかの利用者の実測で変わる段階」の表を出す。
- 1 件の提出が、その構成の値を決める(外れ値は 3 件以上でしか除けない)。

**校正への取り込み**(`python -m genmodelfit.calibrate`):

- そろった(`consistent`)ほかの利用者の実測だけを使う。係数は全モデルに効くので、1 件では入れない。
- 測り方が係数の合わせと同じ(`calibrate.CALIBRATION_METRIC`。今は記録の無い RTX 5080 の 9 件の測り方)なら、係数の合わせと leave-one-out に入る。
- bench の提出は `torch_reserved` なので、今は**照合**(上の表。全件で合わせた係数で当てた誤差)にだけ入る。
- `torch_reserved` の実測が種類ごとに数件そろったら、測り方ごとに固定分を分けて合わせ直す(それまで混ぜない)。

**毎週の点検**(`genmodelfit contrib aggregate --report`。#19 の毎週の自動 PR が呼ぶ):

- その時点の data/contrib をまとめ直し、校正をやり直して、種類ごとの LOO 誤差と照合の誤差を表にする。
- 閾値(既定 25%、`--threshold`)を超えたら警告を出す(`--fail-on-breach` で終了コード 3)。
- 判定に入れるもの:
  - 評価できる種類(張り付いていない実測が 2 件以上)の LOO 誤差
  - ほかの利用者の実測の照合の誤差
- メンテナの照合の行(下の RTX 3070 の 2 件)は既知の外れなので、表には出すが判定には入れない。

**水増し**: 同じ人が同じ構成で何度も出すと、件数が水増しされます。

- 提出に個人を見分ける情報を入れないので、見分けられない。
- 同じ内容(hash)は重複として断るが、測り直した別の値は断れない。
- PR を見る人が、同じ PR に同じ構成が並んでいないかを見る。

### NVIDIA 以外の GPU の bench(0.9.0)

NVIDIA 以外の GPU(AMD・Intel・Apple)は実測が 0 件で、確認済みの種類の印(✓)が付きません(段階は同じ基準。[scoring.ja.md](scoring.ja.md)「確認済みの GPU の種類」)。
実測を集めやすくするため、bench の「GPU が空いているか」の確かめを各社の道具でも行います(`gpustat.py`)。

- Linux の AMD: amd-smi → rocm-smi
- Linux の Intel: xpu-smi
- Windows の AMD・Intel: 性能カウンタ
- Apple: ioreg

読めれば NVIDIA と同じく、使用率 30% で断ります。

道具が無い・読めないとき(rocm-smi の入っていない Linux など)は、`--force` を求めずに測ります。

- 確かめるのは次の 2 つだけ。
  - ComfyUI のキューが空なこと。
  - ComfyUI 以外が使う GPU のメモリが全体の半分以下なこと(Apple の統合メモリでは見ない)。
- warnings と note に「使用率は確かめていない」と残す。
- ComfyUI 以外が GPU のメモリを半分より多く使っていれば、`--force` が無い限り止める。

**`standard` は true のまま**にしました。理由:

- `standard` は「公式テンプレートのままで、ComfyUI でほかの仕事が混ざらず、全部のノードを実行したか」で、ComfyUI のキューの中のことだけを見る。
  キューは開始前・送る直前・測っている間に確かめている。
- 見積もりに使う値(`peak_vram_gb`)は ComfyUI のプロセスの torch の確保量で、ほかのアプリが GPU を使っていてもほぼ変わらない
  (変わるのは時間と、GPU 全体の増分の note)。
- NVIDIA で `--force` を付けて確かめずに測った結果も、これまで `standard` を変えていない(同じ扱いにそろえる)。

その他:

- ほかのアプリと取り合ってメモリ不足で逃がした・失敗した結果は `offload`・`outcome` に出るので、そこで分かる。
- ComfyUI が別の PC のときは、NVIDIA と同じく `--force` が要る(この PC の道具では何も確かめられないため)。
- 実測には `gpu_backend`(cuda / rocm / xpu / mps)を残す。
- 提出には `system.gpu.vendor`・`backend` と、AMD・Intel では PCI の型番 ID(`pci_id`)を入れる。
- xpu-smi で Intel の GPU が 2 枚以上あるときは、どれが ComfyUI の GPU か決められないので、読めないものとして扱う。

Apple の MPS では、ComfyUI の GPU 名が `mps` になります。

- ComfyUI が同じ PC なら、bench は system_profiler で読んだこの PC のチップ名を実測と提出の `gpu_name` にする。
  - 例: `Apple M2 Pro`。`hardware.APPLE_CHIP_NAME` の形に合うものだけで、シリアルなどは入れない。
- 判定はこの PC の GPU 名(同じ system_profiler のチップ名)と比べるので、同じチップの実測が段階の根拠になる。
- 別の PC の ComfyUI・チップ名が読めないときは `mps` のまま(警告を出す)。
- `mps` の実測は会社 apple としてだけ使い、同じ GPU の実測にはならない。
- `contrib validate` は、vendor が apple の GPU 名をチップ名か `mps` だけに限る。
